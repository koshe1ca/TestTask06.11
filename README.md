# Semantic TextNavigator — прототип для Product Owner

Работающее **локальное веб-приложение** для проверки суммы и срока поставки по нескольким TXT-документам. Основание каждого распознанного значения: **имя файла, точная цитата, номер абзаца и переход к этому абзацу**. Никакого платного API, аккаунта LLM или отправки документов в облако не требуется.

> **Важно:** в папке `documents/` находятся **шесть оригинальных учебных TXT-файлов из тестового задания**, предоставленных заказчиком прототипа. При нажатии «Открыть учебный комплект» приложение анализирует именно эти документы. Договоры и суммы вычисляются из содержимого, а не из имени файла или заранее заданного списка ответов.

## Запуск (Windows 10 / macOS / Linux)

Требуется **Python 3.10 или новее** и современный браузер (Chrome, Edge, Firefox, Safari). **Внешние Python-зависимости отсутствуют.**

1. Распакуйте архив `semantic_textnavigator.zip`.
2. Откройте терминал **в папке `semantic_textnavigator`**.
3. Запустите (на Windows можно также дважды щёлкнуть `start_windows.bat`):

   **Windows:**
   ```powershell
   py -3 server.py
   ```
   Если `py` не найден, попробуйте `python server.py`.

   **macOS / Linux:**
   ```bash
   python3 server.py
   ```
4. Откройте **http://127.0.0.1:8501** в браузере.
5. Нажмите **«Открыть учебный комплект»** или выберите **несколько собственных TXT-файлов**. Изменение даты проверки автоматически пересчитывает условия. Для завершения сервера нажмите `Ctrl+C`.

При занятом порте: `py -3 server.py 8502` (Windows) либо `python3 server.py 8502` (macOS/Linux); откройте указанный порт. Сервер слушает **только `127.0.0.1`**.

## Сценарий использования

1. В блоке **«Обзор договоров»** просмотрите три строки: договор, поставщик, сумма, срок и статус. Поиск фильтрует строки, экспорт выгружает CSV.
2. Нажмите на строку договора. Под ней появятся основания для поставщика, суммы и срока. Для действующего изменения показано применённое допсоглашение; письма и проекты вынесены отдельно и **не применяются**.
3. Нажмите **«К источнику»** рядом с цитатой. Откроется вкладка исходного файла с **подсвеченным абзацем**. Можно прочитать весь документ.
4. Во вкладке **«4 вопроса»** получите ответы на все вопросы из задания с первоисточниками.
5. Во вкладке **«Диагностика»** видны типы документов, неподтверждённые связи и причины ручной проверки.

**Контрольный пример для исходных документов на 10.03.2026:** STN-101 — 1 380 000 ₽, срок **30.04.2026** (подписанное допсоглашение от 01.03.2026 меняет исходные 1 200 000 ₽ и 15.04.2026); неподписанный проект предлагает 1 450 000 ₽ и 10.05.2026, **не действует**. STN-102 — 840 000 ₽, поставка 20.03.2026; письмо предлагает 27.03.2026, **не действует**. STN-103 — **«нет данных» по цене** (стоимость определяется отсутствующей спецификацией, бюджетный лимит 600 000 ₽ не цена договора), срок 30.04.2026. Раньше 01.04.2026 по действующим условиям — **только STN-102**.

Проверка изменяемости: поменяйте `840 000` на `975 000` в соответствующем TXT и загрузите набор повторно. Сумма STN-102 обновится вместе с цитатой. Можно добавить четвёртый договор, в том числе с нестандартным заголовком.

## Проверка качества

В корне проекта выполните:

```bash
python -m unittest discover -s tests -v
```

На Windows подходит `py -3 -m unittest discover -s tests -v`. Тесты проверяют API, новую сумму в измененном файле, дату проверки, отсутствующие значения, разбор нестандартного договора, подписанное/неподписанное изменение, конфликт допсоглашений, источник цитаты. **29 автотестов**. Для проверки вручную откройте комплект, сравните цитаты, поменяйте сумму и срок, затем загрузите пустое значение.

## Краткая продуктовая и техническая записка

**Пользователь и потребность.** Специалисту по закупкам нужно за минуты проверить действующие суммы и сроки по нескольким документам, не теряя юридически существенный статус документа и возможность открыть первоисточник. Ценность — сокращение времени сверки при сохранении проверяемости, а не автоматическое юридическое заключение.

**5 вопросов клиенту до следующего этапа:**
1. Как в реальном документообороте проверяется действительность подписи (ЭП, скан, реестр подписей), а также дата вступления в силу?
2. Какие типовые источники и форматы: TXT, PDF, сканы, DOCX, структурированные карточки ЭДО?
3. Как понимать срок: дата одного этапа, график поставок, несколько партий, рабочие/календарные дни?
4. Какие варианты сумм важны: цена с НДС, без НДС, валюта, изменение цены, спецификации и частичная поставка?
5. Кто вправе видеть договоры, предложения, историю исправлений и результаты разных подразделений?

**Допущения.** Дата по умолчанию — 10.03.2026. Идентификатор извлекается **из текста**, не из имени файла. Основной договор — базовое условие. Его изменяет **только** допсоглашение с подтверждением обеих подписей и распознанной датой вступления в силу не позднее даты проверки. Из нескольких вступивших в силу соглашений приоритет имеет более поздняя **дата вступления в силу**, а не дата загрузки. Конфликт одновременных редакций помечается как неопределённый. Письма, проекты и неподтвержденные изменения показываются отдельно. Неизвестные и противоречивые значения — **«нет данных»/«нужна проверка»**.

**Две метрики:**
- **Точность извлечения действующих полей:** доля корректных значений / обоснованных «нет данных» для суммы и срока по размеченной выборке договоров и допсоглашений. Замер по полям, включая случаи конфликта и неподписанных изменений.
- **Медианное время проверки одного договора:** время от загрузки файла до просмотра исходного абзаца с действующим условием. Сравнение с текущим ручным процессом.

**Архитектура:**

```text
Браузер (web/index.html + app.js + style.css)
    ↓ HTTP: JSON (TXT и дата проверки)
server.py (локальный сервер stdlib; входные ограничения)
    ↓
textnavigator/engine.py (тип → связь → поля → статус → приоритет → цитаты)
    ↓
textnavigator/qa.py (4 вопроса из результатов анализа)
    ↓ JSON (значения, проблемы, имя файла, точный абзац)
Браузер (таблица, детали, переход к источнику, диагностика)
```

**3 технических решения / компромисса:**
1. **Правила и регулярные выражения вместо LLM в рабочем цикле.** Нулевые расходы, воспроизводимость и отсутствие сетевой передачи. Минус: слабее на свободном языке, сложных форматах и нетипичных формулировках; вместо догадок выдаём предупреждение.
2. **Хранение доказательств по исходным абзацам.** Можно проследить каждый результат до текста и проверить его. Минус: разбиение на абзацы по пустым строкам грубое; в документах без пустых строк цитата может оказаться большой.
3. **Однопроцессный сервер стандартной библиотеки, данные в памяти.** Запуск на Windows без установок и ключей; нет базы, фоновой обработки, долговременной истории и встроенных прав доступа.

**Что изменится на 100 000 документов и при правах доступа.** Приём документов станет асинхронным (очереди, фоновые воркеры), извлечение и нормализация — с версионным хранилищем и индексом по номеру договора/контексту. Потребуются PostgreSQL или аналог для связей, полнотекстовый поиск, мониторинг качества, хранение оригиналов, повторная обработка при изменении правил. Авторизация, RBAC/ABAC и фильтрация прав на уровне **исходного документа, цитаты, API-ответа и экспорта**, журнал доступа, шифрование и разграничение компаний/подразделений обязательны. Данный прототип не предназначен для такого масштаба.

**Следующие три улучшения (по приоритету):**
1. Подтверждение статуса подписи и дат по метаданным ЭДО/ЭП и расширенные тесты конфликтов (сейчас статус определяется только из текста).
2. Гибридное извлечение на более разнообразных договорах: поиск + локальная LLM/NER при необходимости, обязательно с проверяемой цитатой и ручным подтверждением.
3. Постоянное хранилище документов, версия результатов, доступы и аудит, затем масштабирование обработки.

**Известные ограничения.** Только TXT, русскоязычные формулировки и простые даты/суммы; нет OCR, PDF, DOCX, сквозного юридического анализа, проверки подлинности подписи, сложных расчётов сроков, распределения по партиям или гарантий полноты. Лимиты 30 файлов / 2 МБ на файл. Не отправляйте сюда секреты, если запускаете прототип в ненадёжной среде. Приложение работает на `127.0.0.1`, не предназначено для публичного хостинга.

## Отчёт о вайбкодинге

**ИИ-инструмент:** ChatGPT (GPT-6), использован для разработки Python-парсера, API, браузерного UI, тестов и редактирования текста инструкции. **Характерные формулировки задач** (сокращённая реконструкция рабочих задач, не дословная история):

1. «Сделай минимальный локальный продукт с загрузкой TXT, правилами приоритета и ссылками на точный абзац. Не используй платный API и не вшивай ответы».
2. «Покрой тестами неподписанный проект, письмо, вступление в силу позже даты проверки и отсутствующие значения».
3. «Проверь договор без стандартного заголовка, в котором номер указан отдельно; исправь классификацию, не распознавая документ по имени файла».

**Реально найденные ошибки и исправления:** после получения оригинальных TXT выявлены: неверная обработка суммы с числом прописью в скобках, смешение оплаты и поставки внутри одного абзаца, принятие бюджетного лимита за договорную цену. Исправлены правила извлечения и добавлены регрессионные тесты. Ранее первый тест нестандартного заголовка (`test_nonstandard_contract_layout`) завершился ошибкой: файл классифицировался как `unknown`. Добавлен осторожный запасной путь распознавания договора по сочетанию номера, поставщика и условий в содержимом. Повторный прогон тестов подтвердил исправление. Также добавлен тест на подписанное изменение с нечитаемым новым сроком: вместо устаревшей даты основной договор показывает «нет данных» и предупреждение.

**Выполнено:** парсер, логика статусов, проверяемые цитаты и переход к абзацу, веб-интерфейс, четыре ответа, CSV, оригинальные учебные TXT, автоматические тесты, инструкция. **Не выполнено:** настройка пользовательского деплоя, импорт PDF/DOCX, проверка ЭП. Полный сценарий API протестирован через локальный HTTP; визуальный end-to-end прогон браузера в среде сборки был недоступен из-за административной блокировки локальных URL в Chromium (это ограничение среды проверки, не установленный дефект приложения).

**Затраты времени:** прототип собран в одной рабочей сессии; точный персональный тайм-трекер не велся, поэтому человеко-часы не заявляются. Фактическая длительность сборки в этой сессии по временным меткам команд — около 15 минут; это не оценка человеко-часов промышленной разработки. Ограничение задания «до 4 часов» соблюдено при сборке этой версии.
